# 发布管理台 —— 需求说明书 V1.1

> 2026-10-18。在 V1.0 基础上并入用户第 1 轮追问的 6 个答复 + 新增"版本管理"需求。**V1.0 保留不删**（只迭代不删旧版）。
> 项目/仓库名已定：**mc_sync_server**（客户端 = `mc-sync-agent`，管理台 = "发布台"）。

## 一、需求清单（累计，含本轮新增）

1. **一个网页**，往权威库上传/删除文件，不用再 SSH/SFTP 手工搬。
2. **Mods 带标记**：文件名 / 名字 / 简介 / 类型（服务端·客户端），能删。
3. **删除进回收站**（不是彻底删）。
4. **上传新 mod** + 手动填名字/简介/类型。
5. **刷新清单**按钮（权威库清单立刻更新）。
6. **同步到 MC 服务端**按钮：权威库 → 服务端自己那份 mods **和 config**（新增的复制过去、多的删掉；执行前先看清单）。
7. **Config 目录**：网页里直接在线改文件（编辑器 + 自动留旧版）。
8. **其它目录**：能管理（**本轮起也开上传**）、能看清（多大 / 最后修改时间 / 谁动的）。
9. **做成能开源给别人用的正式项目**（别用临时框架）。
10. **【本轮新增】版本管理**：上传覆盖 / 删除 / 在线改，都能还原到之前的某个版本。

## 二、拍板结果（累计）

| 问题 | 决定 |
|---|---|
| 服务端怎么搭 | 统一成 Node 一套（旧 Python 那半先搬+跑同样测试+真机冒烟比对，确认不退化再切；旧的可一句话切回） |
| 代码放哪 | 另开干净新仓库 **mc_sync_server**，只放我们这套；对上游 ServerSync 在文档致谢 + 标 GPL 来源 |
| 给别人用的程度 | 配置化 + 中英文说明 + 一键 Docker；不做多用户/权限体系 |
| 重启按钮 | 要（改完 mod/config 一键重启 MC 服务端实例） |
| 项目名 | **mc_sync_server**（用户起的） |
| 回收站保留 | **做成配置**：按时间（默认 30 天）**和**按大小（默认 2 GB），超了自动清最老的 |
| 其它目录上传 | **开**（和 mods 一样的上传/删除，但不带名字/简介/类型字段） |
| 客户端 agent 包 | **能管**，分两档，见 §五 |
| 服务端 config 同步 | **要**（和 mods 一起同步到服务端实例） |

## 三、界面结构（四页 + 动作）

**顶部**：连接状态、权威库版本号、mods/config 计数、最后上交时间；`刷新清单`、`退出`。

| 页面 | 内容 |
|---|---|
| **Mods** | 表格（文件名/名字/简介/类型/大小/上传时间/操作）；`上传`、`同步到 MC 服务端`、搜索、类型筛选；多选批量改类型/删。每行有 `历史`（看这个文件的旧版本、一键还原）。 |
| **Config** | 左文件树 + 右在线编辑器（行号、搜索、保存、放弃改动）；保存自动留旧版 + 刷新清单。每个文件有 `历史`。 |
| **其它目录** | 只读表格（目录/文件、规则、大小、最后修改、谁动的）+ **上传/删除**（删除进回收站，也有 `历史`）。禁区不出现。 |
| **回收站** | 谁在什么时候删的、为什么、`恢复` / `彻底删除` / `清空`。保留策略走配置。 |

**动作**：`上传`（mods 自动读名字简介；其它目录直接传）、`删除→回收站`、`同步到 MC 服务端`（mods+config，先看清单，覆盖/删除进回收站+历史）、`重启实例`。

## 四、字段与规则

**Mods 元数据**（存仓库外）：文件名（主键）、名字、简介、备注、类型、大小、上传时间、来源。
**类型三档**：`两边都要`（默认）、`服务端也要`、`只有客户端`；只有前两档会同步到服务端。
**现状预标**：文件柜 254 个里 **28 个纯客户端 mod**（angelica、EuphoriaPatcher、nech、MouseTweaks、Schematica、tcnodetracker、UniLib…）开工时预先标好，剩下的默认 `两边都要`。

**两条安全阀**：① 执行前先给"将新增/将覆盖/将删除"清单；② 所有删除/覆盖都进回收站并留历史版本，能一键还原。

**config 同步的风险提示**：config 没有天然的"客户端/服务端"之分，整份盖过去会把服务端特有的值一起冲掉。所以：**同步前先给差异清单**（哪些文件两边不同、会覆盖成什么），确认才执行；配合版本管理随时还原。现状两边 config 源自同一套 modpack，基本一致，首轮同步预计只是补缺。

## 五、客户端 agent 包怎么管（两档，待用户选）

**权限**：不麻烦——客户端本来就在往自己的 `I:\gtnh-sync\` / `G:\gtnh-sync\` 写东西，换个 jar 不存在额外权限问题。麻烦的是"开机自动换新版"要动 `-javaagent` 那一层（开机那一刻从本地路径读的），不能直接读网上的 jar。

| 档 | 做法 | 成本 |
|---|---|---|
| **A（推荐先做）** | 面板存"最新 agent jar + 版本号"；客户端每次启动时顺手**上报自己跑的版本**（它本来就在跟服务器说话）→ 面板上能看到"哪台机器还在跑旧版"，点一下给个下载/更新提示 | 便宜 |
| **B（第二版）** | 每台机器放一个几行的"**自更新壳**"（永远不变），开机先从服务器拉最新 agent 再跑，断网时用上一次拉到的那份兜底 | 稍贵，一劳永逸 |

## 六、版本管理（需求 10）

**不麻烦**。底层每次改动本来就在留快照，把它做成"按文件的版本历史"即可：
- 上传覆盖、删除、在线改配置 —— 改动前都先把旧文件复制一份到历史目录（带时间戳 + 谁改的 + 为什么）。
- 面板里每个文件有 `历史`：列出旧版本，点一下 `还原`（还原本身也留历史，还能再翻回来）。
- 历史目录在仓库外，**不进客户端清单**（客户端永远只看到"当前最新"）。
- 保留策略和回收站共用一套配置（按时间 + 按大小）。

## 七、安全

- 管理台口令登录；客户端接口（清单/取文件/上交）不需要口令（各有各的令牌）。
- 面板只对 Tailscale / 内网可达，**不暴露公网**（一次性确认）。

## 八、技术口径（给干活的人看）

- 一个 Node + TypeScript 服务：① 客户端清单/取文件/上交（从 Python 搬，含账号档案）② 管理台 API ③ 管理台前端（Vue 3，打包成静态文件由它发）。
- 前端：Vue 3 + 现成组件库 + 现成代码编辑器轮子（config 在线改）。
- 配置驱动：目录清单/规则、实例路径、服务端 mods+config 路径、口令、回收站/历史保留策略，全写配置；默认值就是现在这套 GTNH。
- 交付：中英文 README + `docker run` + 手动部署说明。
- 迁移：Python 那半搬到 Node，先跑同样 24 测试 + 真机冒烟比对，一致再切，旧的可一句话切回。

## 九、一次性准备（我来做）

1. E3 装正式 Node。
2. 给服务端 mods 目录开写权限（config 目录同理）。
3. 拿一个 MCSManager API key（重启实例用）。

## 十、验收标准

1. 面板能上传/删除/改类型/在线改 config，清单随之刷新，客户端下次开游戏自动生效。
2. "同步到 MC 服务端"执行后，服务端 mods+config = 权威库里的（两边都要 + 服务端也要），多余进回收站。
3. 回收站能恢复；**每个文件能看历史、一键还原**。
4. 其它目录能上传/删除/看清大小时间谁动的。
5. 一整轮（改 → 同步 → 重启 → 客户端更新）不碰 SSH/SFTP/MCSManager 面板。
