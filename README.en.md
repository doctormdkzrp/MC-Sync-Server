# MC Sync Server

English | [简体中文](README.md)

[![License](https://img.shields.io/badge/license-GPL--3.0-blue.svg)](LICENSE)
[![Node](https://img.shields.io/badge/node-%3E%3D%2020-informational.svg)](https://nodejs.org/)

A synchronization service for Minecraft modpacks: **the server holds the single authoritative copy of the
pack; clients align themselves to it before launch and submit their per-player data on exit.**
A built-in web console covers the whole workflow — adding mods, editing configs, pushing changes to the
running server instance and restarting it.

> [!IMPORTANT]
> **All code in this repository was generated by AI.** Requirements, review and verification were done by a
> human; the implementation was written by AI. Treat it as an experimental implementation — review the code
> and test it yourself before using it in production.

## Overview

For a large modpack (several hundred mods, e.g. GTNH), adding a single mod normally means maintaining
several copies: one for the server, one in the file repository, and one in every player's client. Config
changes have to be replicated machine by machine. At the same time, key bindings and minimap data are
inherently per-player and must not be overwritten by someone else's copy.

This project reduces that workflow to three steps:

1. Upload a mod or edit a config in the console, then click **Sync to MC server**.
2. Player clients run an agent that aligns the local instance with the server before the game starts.
3. Key bindings and map data are submitted on exit and **merged** by the server rather than overwritten.

## Features

- **Central management of the authoritative repository** — mods, configs, resourcepacks and scripts are
  uploaded, tagged, edited and deleted from the web console.
- **Differentiated sync strategies** — mods are filtered by type (client-only mods are never pushed down);
  configs only overwrite files that exist on both sides, never adding or deleting server-specific files.
- **Preview and backup** — additions, overwrites and deletions are listed for confirmation before the sync
  runs, and every overwritten file is backed up.
- **Recoverable operations** — deleted files go to a recycle bin; configs keep a per-file version history.
- **Self-updating client** — agent packages are distributed and hash-verified by the server, so jars no
  longer have to be replaced by hand on every machine.
- **Instance restart** — the console can restart the MC server instance through the MCSManager panel API.

## Components

| Component | Responsibility | Stack |
| --- | --- | --- |
| **Server** | Serves the sync manifest, provides files listed in it, accepts union submissions from clients; also hosts the console API and static pages | Node.js + TypeScript + Fastify |
| **Web console** | Mods management, online config editing, other directories, version history, recycle bin, sync to the MC server, instance restart, agent package distribution | Vue 3 + Vite (build output served by the server) |
| **Client agent** | A `-javaagent` attached to the client JVM: aligns local files with the manifest before launch, submits the union archive on exit | Java 17 |
| **Bootstrap shell** | A tiny, stable javaagent that queries the server for the current agent version and replaces itself with it; falls back to the local copy when offline | Java 17 |

The sync API and the console are served by the same process, so **the service address is the console address**.

## Status

The sync API, web console, client agent and the self-updating shell all work end to end, verified against a
real 250-mod GTNH instance. Milestone state is tracked in [`docs/PLAN.md`](docs/PLAN.md).

## Requirements

- Node.js >= 20 (server)
- JDK 17 (only when building the client agent yourself)
- Docker or systemd (production deployment, optional)
- MCSManager panel (for the "restart instance" feature, optional)

## Quick start

### 1. Build and run the server

```bash
cd packages/server
npm install
npm run build
node dist/server.js --config /path/to/config.json
```

See [`deploy/config.example.json`](deploy/config.example.json) for a complete example. The fields you
usually need to adjust:

| Field | Description |
| --- | --- |
| `repo_root` | Root of the authoritative repository, containing `mods/ config/ resourcepacks/ scripts/ …` |
| `listen` | Address and port to bind |
| `admin.token_file` | File holding the console password |
| `submit_token_file` | File holding the client submission password |

Passwords are always read from files, so they never appear in the config or in git. The startup log prints
the address and port actually bound.

### 2. Open the console

Open `http://<host>:<port>/` in a browser and log in with the admin password. The console has four pages:

| Page | Purpose |
| --- | --- |
| **Mods** | Upload mods (name and description are read from the jar), tag them by type (both sides / server only / client only), edit and delete (to the recycle bin) |
| **Config** | Edit configuration files online (line numbers, search); the previous version is archived before every save and can be restored at any time |
| **Other dirs** | Manage resource packs, scripts and similar directories: file sizes, timestamps, upload and delete |
| **Recycle bin** | Restore deleted files; retention is bounded by both age and total size |

After changing mods or configs, click **Sync to MC server**: the console lists the number of files to be
added, overwritten and deleted for confirmation before anything is touched, and overwritten files are kept
as backups. Mod changes require a **restart of the server instance** to take effect.

### 3. Attach the client agent

Add one line to the client's JVM arguments (identical for Prism Launcher, HMCL and the vanilla launcher):

```
-javaagent:<path to agent.jar>=<path to local config json>
```

- **`agent.jar` can be shared by every machine**;
- **the config JSON is per machine** (`instancePath` differs, other fields can be copied);
- switching accounts on one machine needs no new jar — the agent reads the current account from the launcher
  and matches the corresponding profile.

To avoid distributing jars by hand in the future, use the bootstrap shell `gtnh-sync-bootstrap.jar` in place
of the agent jar; the config JSON stays the same. See
[`packages/agent-bootstrap/README.md`](packages/agent-bootstrap/README.md).

## Common operations

| Goal | Steps |
| --- | --- |
| Add / replace a mod | Console → Mods → upload → tag type → Sync to MC server → restart the instance |
| Change a config | Console → Config → edit → save → Sync to MC server → restart the instance |
| Release a new client agent | Upload the new versioned jar on the Agent page; clients running the bootstrap shell pick it up on their next launch |
| Undo a mistake | Restore from the recycle bin, or roll back a config from its version history |
| Check client versions | The Agent page lists each machine's client version and last-seen time |

## Deploy

Use Docker ([`deploy/Dockerfile`](deploy/Dockerfile) +
[`deploy/docker-compose.yml`](deploy/docker-compose.yml)) or systemd
([`deploy/mc-sync-server.service`](deploy/mc-sync-server.service)); both require Node.js >= 20.

## Layout

```
packages/server           Node + TypeScript + Fastify — sync API + console API + static file server
packages/web              Vue 3 + Vite console (built into packages/web/dist, served by the server)
packages/agent            Java agent: aligns your instance before launch, submits on exit
packages/agent-bootstrap  Tiny, stable javaagent shell that self-updates the agent
deploy/                   Dockerfile, docker-compose, systemd unit, config example
docs/                     ARCHITECTURE.md (the contract), ADMIN_API.md, SPEC.md, PLAN.md
```

## Development and testing

```bash
# server
cd packages/server && npm install && npm test && npm run build

# web console (build output is served by the server)
cd packages/web && npm install && npm run build

# client agent (JDK 17 required)
cd packages/agent && gradle build
```

The documented interfaces are authoritative: update
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) (client sync protocol) and
[`docs/ADMIN_API.md`](docs/ADMIN_API.md) (console API) before changing an interface.
